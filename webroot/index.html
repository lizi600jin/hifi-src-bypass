一键预设

点一下即完成「设置 + 应用 + 重启音频服务」，不用逐个调下面的参数。
「自动识别」会读小尾巴对内上报的最高采样率与位深，自动挑一个不超过它、且本模块支持的档位 —— 换耳机/换小尾巴后点一下就行。

直通设置

系统混音器的工作频率。当它与音源一致时，AudioFlinger 会跳过自身重采样 —— 这是让所有 App都免于 SRC 的关键开关。默认档与原厂一致，最稳妥。

注意：AudioPolicyManager 对混音输出取的是列表里的最大值，所以本模块会把混音端口重写成唯一一个你选的频率 —— 只往列表前面加一个 44.1k 是没用的，48k 仍然是最大值。请按曲库多数采样率选档。

USB / 有线的 DIRECT 直通通道的最高采样率。按解码芯片的真实上限设置，不要盲目拉满。
· CX31993 上限 384 kHz / 32-bit，配 MAX97220 耳放。
· 96 kHz / 24-bit：多数 96k 上限的数字小尾巴请选这一档。
· 它真正的短板是位深：原厂通常只给 16bit，本模块补上 24/32bit 才是收益所在。

接上小尾巴后，USB 音频不走混音器，而是走厂商的 HiFi 专用端口（如 hifi_playback）。它原厂是「动态」的，会被钉在小尾巴上报的最大率上，于是所有音源都被上采样、没有一条能比特完美。
请按你正在听的音源手动选档：网易云「超清母带」/ QQ 音乐「臻品音质」多为 192 kHz；96k 母带选 96 kHz。选对档后，该率的内容比特完美；其余率的内容会被上采样（带限插值，不丢内容）。
关键：永远不要往下选 —— 锁定的率低于音源率会发生有损下采样（超声频段被滤掉）。auto = 原厂行为。

USB / 有线输出端口允许的位深上限。16bit 永远保留作基线，所以这是"上限"而不是"唯一"：
· 16-bit = 只留 16bit（最保守，排查用）。
· 24-bit = 16 + 24bit。96k 上限的数字小尾巴选这一档。
· 32-bit = 16 + 24 + 32bit，最宽松，默认。
设为高于解码器能力的位深可能导致无声。

手机扬声器 / 听筒输出端口的采样率。原厂通常锁在 48 kHz：播放 44.1 kHz 音乐时会被系统重采样到 48 kHz。钉死为曲库采样率可让扬声器回放也免于 SRC。
· auto = 原厂行为（推荐，最稳妥）。
· 选定档位后，扬声器端口只保留该采样率 —— 其余率的音源会被上采样（不丢内容），永远不要往下选。

扬声器 / 听筒端口允许的位深上限。手机内置 DAC 多为 24bit 能力，但原厂策略常只声明 16bit。
· 16-bit = 保持原厂（默认，最保守）。
· 24 / 32-bit = 补齐到该档位。设为高于硬件能力的位深可能导致扬声器无声。

高通 QTI 音频 HAL 原生支持系统属性 persist.vendor.audio_hal.dsp_bit_width_enforce_mode：设为 24 / 32 时，audioserver 启动即通过 "ASM Bit Width" 混音控制器把 ADSP 的 ASM 流强制到该位宽。
· 16（关） = 不注入任何属性（原厂行为，ADSP 按内容位深处理）。
· 24 / 32-bit = 点「应用并生效」时注入，重启音频服务后生效；一键还原会自动清除。
纯属性层操作，不改写任何原厂文件。

应用「扬声器最佳实践」:44.1kHz + 24bit + 零重采样（对齐 44.1k 曲库）。HiRes 实验档请在终端跑 hifi speaker hires。

声明 Android 14+ 的 BIT_PERFECT 输出端口（hifi_output）并接入各播放路由。仅 AIDL 方言（高通新机型）生效：HIDL 机型在「应用」时会被直接拒绝。播放器须用 preferred mixer attributes API 主动请求，未请求则走原混音路径，无副作用。

关闭则改动在下次重启手机后生效，更稳妥。

一键还原

无损 · 可逆
  • 点「一键还原」＝立刻卸载绑定挂载，回到原厂音频策略，并重启音频服务。当前播放会中断，属正常现象。
  • 还原是无损的：模块从不写入系统分区，原厂音频策略 XML 始终原封不动，只是上面盖了一层临时文件。
  • 还原后模块仍然装着但处于停用状态，你设过的参数会保留，再点一次「应用并生效」就回到原来的配置。
  • 想彻底清除：在 KernelSU / Magisk / APatch 里卸载本模块。卸载脚本会自动卸载挂载、清理 /data/adb/hifi_src_bypass 的全部残留并还原原厂策略。

深度校验（四层证据）

—

跑一次 hifi doctor（只跑 [1]–[7]），把「到底有没有真正生效」拆成四层证据：
A 配置层 生效文件里端口的上限与位深 → B 系统层 audioserver 读到的内容 → C 能力层 解码器声明支持什么（不代表在跑）→ D 链路层 此刻真正协商出的 rate / format 与占用进程。
D 层显示 closed 有三种完全不同的含义，会自动判定是哪一种：
· D1 找到 0 个 pcm 目录 = 本机内核没导出这棵树（不是模块没生效，改检测也没用，以 5b/5c 为准）；
· D2 有目录但全 closed = 检测时暂停了，或播放器正用自带 USB 驱动独占；
· D3 有打开的流 = 出明细。
5c 段会直接点名网易云 / QQ音乐 / 海贝此刻走的是直通、混音路径还是没走音频栈。
末尾 [7] 就是当前实际输出状态速览，一屏可见。换机型 / 刷入无效要发给维护者的那一段（原 [8]）已移到下面的「机型适配校验」。

机型适配校验

—

这一块解决什么：当你换了机型、或刷入后完全无效时，需要把「本机的病历」发给维护者。 它和上面的深度校验是独立的，所以深度校验窗口一打开就是实时输出状态，不用再往下翻找。
跑的是 hifi adapt（等于 HIFI_PROBE_SECTION=adapt hifi doctor），只做检测、不改任何东西，回答三件事：
① 这台机器到底有哪些策略文件，模块为什么补了它 / 跳过了它（含上次扫描的逐条结论）→ ② 策略基线是什么（模块挂载的东西是从哪份原厂件生成的）→ ③ 音频输出在系统里的真实路径（Config source 指向哪份文件、逻辑端口名、内核设备节点与声卡号）。
反馈时请把这一整段连同上面深度校验的「排查明细」一起发回来，再补一句：型号 / 系统版本 / 小尾巴型号 / 具体现象。

原理与边界

  • 只替换本机原厂音频策略 XML（如 /odm/etc/audio/... 或 /vendor/etc/...），用 systemless 绑定挂载，不写入任何分区，卸载即恢复。
  • 以本机原厂配置文件为唯一基线重建，只改采样率与位深，不增删任何混音端口 / 设备端口 / 路由；麦克风、蓝牙、扬声器、空间音频、硬件 FLAC 解码全部保持原样。
  • 本模块把 USB / 有线的 DIRECT 直通端口上限提到你选的档位，并补齐 16 / 24 / 32-bit 三种位深 —— 网易云音乐的「独占 USB 输出」、Apple Music、QQ 音乐 Hi-Res、海贝、UAPP 等走的都是这条 DIRECT 通道。
  • 位深通常才是真瓶颈，不是采样率：原厂 USB 端口的采样率往往本就够用，却只给 16bit。所以本模块对只到 96k 的设备的收益就是「补上 24bit」。位深上限按解码器实际能力选，选高了会无声。
  • 「全局 384 kHz」在 Android 上不存在：系统混音路径必然有固定工作频率。本模块提供的是两条正交的能力 —— ① App 主动申请的独占/DIRECT 直通可达高采样率；② 把全局混音率对齐曲库以消除所有 App 的重采样。
  • 硬件 FLAC / APE 硬解通道（compress_offload_out）按原厂保留，未做提升：这些解码器本身有频率上限，强行提高会导致无声。
  • 若出现无声：点「一键还原」，或卸载模块后重启。
